## Architecture and Data Flow

JiraMentions reads a sanitized projection and selected detail snapshot from useJiraMentionsStore. The main-owned service/repository remain the authorities for Jira data, counts, reply policy, cache, and validated external actions. The renderer will reorganize existing metadata and comments without requesting fields or transforming the durable projection.

An initial `select` may request detail before the existing refresh has populated the service's in-memory field catalog; in that case `getIssueDetail` returns the unchanged cached snapshot with no custom labels. `start()` launches its first refresh asynchronously, and `refresh('open-if-stale')` can return a fresh cached projection without joining it, so the store must not use that IPC response as proof of catalog readiness. `receiveProjection` already handles both refresh IPC results and the existing `jira-mentions:state-changed` event. Track a pending refresh attempt when a projection is `loading`, keyed by `lastAttemptAt` and an in-memory refresh-attempt generation; when that same attempt transitions to a terminal `ready`, `partial`, or `error` projection, reconcile the currently selected visible issue through the existing `jira-mentions:get-issue-detail` IPC. Consume the attempt once so the broadcast and an IPC result cannot start duplicate rereads. If selection changes, clears, or becomes invisible before completion, never reread or commit detail for its old tuple; if another issue is currently selected, reconcile only that current tuple. This repository detail read does not make another Jira request. Commit a response only when the selected `(issueId, incomingCommentId)` and the current monotonically increasing `detailRequestGeneration` still match. Increment the generation whenever a detail request starts (selection or refresh reconciliation) and invalidate outstanding requests on clear or projection-driven deselection; this makes overlapping rereads latest-request-wins. The reconciliation updates only `detail`: it preserves selection, drafts, reply feedback, and current detail while the request is pending; a stale response is discarded, and a failed reread leaves the current detail intact.

For the two named custom people properties, JiraMentionsClient will retain an in-memory catalog descriptor `{ id, name, userValued }` for every custom field ID returned by the existing `/rest/api/3/field` response, and JiraMentionsService will memoize those descriptors per config generation in `customFieldCatalog`/`customFieldCatalogGeneration`. Derive the issue-detail query IDs from the exact same `userValued` subset used today; the remaining descriptors exist only to detect a same-name non-user duplicate. Resolve names by exact case-insensitive equality across all custom field IDs, so duplicate IDs are ambiguous regardless of schema. `fetchIssueSnapshot` continues to return users with only their existing `field:<id>` sources, and the repository persists those arrays unchanged. In `JiraMentionsService.getIssueDetail`, map unique eligible descriptor IDs to their canonical property labels and add a transient `field-name:dev tester` or `field-name:main dev` marker to matching users in a cloned response. The original repository snapshot and source arrays are never mutated or written. No field names or custom properties are added to JiraIssueMetadata, shared IPC types, or database records. JiraMentions derives the rail values from these transient markers in the selected `detail.users`; unrelated `field:<id>` users remain suggestion candidates only and are not rendered as rail properties.

The selected mention remains keyed by issueId and incomingCommentId. The detail snapshot is already returned with comments ordered by creation time and stable comment ID. The selected comment anchors the displayed chronology; renderer-only partitioning places strictly later/equal-tie ordered context above and earlier context below. Use compareCommentsAscending as the canonical tie rule and never use updatedAt for display order.

The attachment preview provider remains scoped to the selected mention tuple. Keep loaded bytes and in-flight Promises in the current memory-only provider scope, and rely on the existing main-process attachment-ID boundary for all image/non-image actions. A selection change must invalidate the prior renderer view even if the issue ID is unchanged.

Responsive layout and visual matching belong to the Jira Mentions component. Use mockup #4 as the specific baseline for inbox compactness, separators, rail rhythm, reply framing, and comment-row emphasis; extend the existing partial JiraMentions.css rules with responsive classes and container/viewport queries. Keep colors, borders, focus, and text treatment sourced from theme.ts, never the prototype's raw CSS values. Main-process changes are limited to internal catalog-descriptor plumbing and response-only decoration in JiraMentionsService. The only renderer-store behavior change is the guarded, existing-IPC selected-detail reconciliation tied to the matching `loading` to terminal refresh transition; no repository, shared type, IPC signature, database schema/write, or settings changes are expected.
