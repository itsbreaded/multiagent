## Verified Repository Facts

- `src/renderer/src/styles/theme.ts` is the existing JS/TS source for app colors, radii, shadows, overlay/menu/sidebar styles, and scrollbars. It has input, border, text, and accent colors, but no reusable field-state contract.
- Its current `ui` export exposes literal appearance values directly, so inline component styles capture the default values instead of resolving an active theme at the document root.
- `src/renderer/src/assets/main.css` is the only renderer-wide stylesheet besides Jira Mentions' feature stylesheet. It imports Tailwind, defines a second set of root color variables, applies the body theme, and styles shared scrollbars. It defines neither a global dark native-control scheme nor a shared focus ring.
- `src/renderer/src/main.tsx` imports the global stylesheet before rendering the application, so theme-derived CSS variables can be installed before the first render.
- Most renderer UI uses inline React styles. `JiraMentions.css` is the existing feature stylesheet and already maps focus, caret, and snooze-field colors from the theme. Settings, Session Browser, Command Palette, Directory Picker, and inline rename fields have independent field styling.
- The two `type="number"` controls are Jira Settings' refresh interval and Jira Mentions' snooze duration. The former uses `fieldStyle` without a dark scheme; the latter gets `color-scheme: dark` and green focus styling from `.jira-mentions-snooze-fields`. Scrollback and idle timeout are text inputs with `inputMode="numeric"`, so they do not have native number steppers.
- Provider checkboxes set `accentColor` locally; other settings/Jira checkboxes do not. A complete rule should cover all checkbox uses rather than only numeric controls.
- Settings, Session Browser, Command Palette, provider confirmation dialogs, and menus already consume `overlayStyles` or `menuStyles`. Directory Picker repeats overlay colors and framing inline. `SnapOverlay` is a specialized pane-drop affordance, not a modal.
- Electron coverage already exists in `e2e/startup.spec.ts` for Settings, Session Browser, Command Palette, and detached-window singleton ownership, and in `e2e/jira-mentions.spec.ts` for synthetic Jira configuration and Mentions behavior. The Jira test asserts dark `color-scheme` on both the snooze number field and, after follow-up verification, its select. User feedback exposed that the prior E2E harness showed windows and launched an external browser; R14/T8 adds a mandatory hidden-window and loopback-only test policy before further suite runs.
- `AGENTS.md` has a `UI & command registry` guardrail group and a docs index. It already requires use of theme tokens for overlays, shared dark scrollbars, icon assets, and common pieces, but it has no complete control/style checklist.
- Jira Mentions has no renderer context-menu handler, while terminal and sidebar surfaces have local custom menus. The main process has no general `webContents` context-menu listener; the [Electron Context Menu guide](https://www.electronjs.org/docs/latest/tutorial/context-menu) states that Electron does not show a context menu by default.
- `docs/testing.md` documents the Vitest renderer project and the Electron Playwright harness. `package.json` exposes `typecheck`, `build`, `test`, `test:watch`, `test:coverage`, `test:db`, and `test:e2e` scripts.

## Architecture and Data Flow

`theme.ts` will distinguish the literal token values of `defaultTheme` from semantic `ui` references that resolve through CSS custom properties. A typed `ThemeDefinition` and root installer will map any conforming, complete token set to those properties; `main.tsx` installs `defaultTheme` before rendering. Every renderer-owned palette value found in T1 must either be represented in this contract—including unique feature and semantic state colors—or have a named reason to remain invariant. This keeps components responsive to the active theme while keeping actual default values in one named place. `main.css` will consume the same variables for global CSS, native control scheme, shared control classes, and scrollbars. Feature CSS will reuse those variables and common control classes, then add only layout-specific rules. Inline styles may express local sizing and layout; they must not hardcode theme-controlled palette values or override shared focus/native-scheme states without a documented reason. This work adds no selection or persistence UI and no second built-in theme.

The shared control contract should expose base and semantic variants for text fields, textareas, selects, number fields, and checkboxes. Keyboard focus remains visible with the app's green accent. Native controls inherit the dark scheme so menus and steppers are consistent. Jira Mentions keeps its compact dimensions and wrapper focus treatment while sharing the same theme variables and control states. Existing `overlayStyles`, `menuStyles`, and `dark-scrollbar` remain the shared overlay/menu/scrollbar entry points.

For the Jira Mentions text-menu exception, the renderer requests a native edit menu only when a right-click originates in an editable text control or on an existing text selection. The main process creates the menu for that request and anchors it to the sending window. Editable controls get applicable editing actions; selected read-only text gets Copy. The menu does not replace sidebar or terminal context menus, and its OS-managed appearance is not part of the app palette.

## Risks, Migration, and Rollback

- Global focus and color-scheme rules can alter controls that currently rely on native defaults. Mitigation: migrate audited controls explicitly, add computed-style assertions for focus and native scheme, and inspect screenshots at main and detached window sizes.
- Some literal colors encode meaning or state, not theme duplication. Mitigation: use T1 dispositions and T5 review; retain status colors unless the value is a duplicate of a shared token.
- Tailwind Preflight and inline React styles can override intended control appearance. Mitigation: verify computed styles in Electron after migration; remove conflicting inline color/border/outline properties instead of escalating selector specificity.
- A broader color migration could change highly tuned feature layouts. Mitigation: only replace common style values and retain explicit local geometry and semantic variations.
- If screenshot comparison reveals a true product-style choice not covered by the spec, stop that change and return to `brainstorm-spec`; do not infer a new brand or control behavior from platform defaults.
